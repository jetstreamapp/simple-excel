# simple-excel goldens

Our own writer's output: the canonical workbook in three container/string variants, generated by script from
`test/helpers/canonical-writer.ts` (the same builder the golden-bytes suite pins) and registered in the manifest.

```
node --import tsx fixtures/generators/canonical-simple-excel.mjs   # all three variants
npm run oracle -- --tag generator:simple-excel --label phase-b-writer
```

| Golden                  | What it shows                                                                            |
| ----------------------- | ---------------------------------------------------------------------------------------- |
| `canonical.xlsx`        | the defaults: bounded shared strings, deflate, zip64 auto                                |
| `canonical.inline.xlsx` | every string inline, no `sharedStrings` part at all (EC-SST-ABSENT-INLINE-ONLY)          |
| `canonical.zip64.xlsx`  | zip64 in every local header on a small archive (EC-ZIP64-SMALL) - SheetJS cannot open it |

Automated verdicts (Open XML SDK validator, Excel via AppleScript, LibreOffice, SheetJS, openpyxl, calamine,
office-kit, and our own reader) are in `research/05-compatibility-matrix.md`, runs `phase-b-writer`,
`phase-d-office-kit-on-ours` and `phase-d-simple-excel-golden`. What is _not_ automated is below.

## Manual: the three applications that cannot be driven from here

Google Sheets is a web app, the Numbers AppleScript import produces empty documents on 14.4
(`fixtures/golden/numbers/STEPS.md`), and there is no Windows machine in the loop. All three are opened by hand
before 1.0. Do each against `canonical.xlsx` (Excel for Windows: all three files), and record the outcome in the
table at the bottom - a banner, a repair prompt or a silently changed value is the finding, whether or not
anything looks broken at first glance.

### What to look for

`Data` sheet (columns are named in row 1; 30 data rows follow):

| Cell           | Should be                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `D7`           | two lines - `crlf` then `line2` (a CR+LF we wrote as `_x000D_` + a real newline)                                                                                                                                                                                                                                                                                                                                                                                                                      |
| `E2`/`E3`/`E4` | `a`+U+0001+`b`, `x`+U+001F+`y`, `bell`+U+0007 - control characters kept, not stripped                                                                                                                                                                                                                                                                                                                                                                                                                 |
| `F2`/`F3`      | the literal text `_x0041_` and `_x005F_x0041_`, **never** `A`                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| `G2`           | the literal text `=SUM(A1)` - text, not a formula, and not a computed `0`                                                                                                                                                                                                                                                                                                                                                                                                                             |
| `H2`           | `00123`, leading zeros intact and left as text                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| `I2`/`I4`      | stored values `9007199254740991` and `12345678901234568`. Sheets and Excel display at most 15 significant digits (`9.0072E+15` under Automatic, `9007199254740990` / `12345678901234600` under `0`) AND truncate numbers typed into formulas to 15 digits, so check without typing them: `=I2=2^53-1` → TRUE, `=I3=2^53` → TRUE, `=MOD(I4,100000)` → 34568 (a value rounded to 15 digits gives 34600; Sheets' `MOD` rejects a dividend more than ~1.1e12 times the divisor, hence the larger divisor) |
| `J11`          | the maximum double: displays as `1.79769313486231E+308` (15 significant digits); `=J11>1.79769313486231E+308` → TRUE proves the full value survived. `inf`, `#NUM!` or an empty cell is the failure                                                                                                                                                                                                                                                                                                   |
| `M2`/`M3`/`M4` | `1899-12-31T00:00:00` as ISO **text** (ADR-003: we do not write pre-1900 serials), then `1900-02-28` and `1900-03-01` as dates. **Google Sheets shows M3 as `1900-02-27`**: it has no fake 1900-02-29 and displays Excel serials 1-59 a day early (EC-DATE-1900-LEAP-BUG); that is Sheets, not the file - Excel and LibreOffice show 02-28                                                                                                                                                            |
| `N2`           | the time of day 12:34:56.789, not a date. The `hh:mm:ss` format rounds the display to `12:34:57` (Excel and Sheets alike); `=TEXT(N2,"hh:mm:ss.000")` → `12:34:56.789` proves the milliseconds survived                                                                                                                                                                                                                                                                                               |
| `O2`/`O6`      | `2024-03-10 03:30` (the golden was generated on a US Pacific machine where 02:30 does not exist that day, so the file holds 03:30 - EC-DATE-DST-GAP, the `dst-gap-shift-1h` policy) and `1900-01-01 12:00` (serial 1.5). **Google Sheets shows O6 as `12/31/1899 12:00`** - its one-day offset for serials below 61, same as M3                                                                                                                                                                       |
| `R31`          | a 32,767-character cell, intact                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| `S30`          | the 40,000-character cell truncated to 32,767, ending `...(truncated)`                                                                                                                                                                                                                                                                                                                                                                                                                                |

`Features` sheet - what our writer does emit: `A1:C1` merged, the first two rows frozen, autofilter over
`A2:C12`, column widths, and cached values where the canonical workbook has formulas (`B3` the concatenated
string, `B4` `#DIV/0!`, `B5` `#N/A`, `B6` a literal `#N/A` error cell). It deliberately does **not** write the
hyperlink, note, rich text, data validation, conditional format, hidden row or hidden column - the reasons are in
`canonical.features.json`, so their absence is expected and not a finding.

Workbook: four sheets in order - `Data`, `Features`, `It's a very long sheet name 001` (31 characters, with an
apostrophe) and `Hidden`, which must still be hidden.

The `O2` DST note: when the writing host is in a timezone where 2024-03-10 02:30 does not exist, that value is
written an hour later on purpose (`dst-gap-shift-1h` in the matrix). Seeing 03:30 is expected.

### 1. Google Sheets

1. Upload `fixtures/golden/simple-excel/canonical.xlsx` to Google Drive and open it with Google Sheets (this
   converts it to a native Sheet). Note any conversion or "features lost" notice - the notice itself is a result,
   record it even when nothing looks wrong.
2. Walk the checks above. Known Google behaviour from the ExcelJS golden: it fully decodes `_x005F_x0041_` on
   import, so `F3` is expected to differ. Anything else is a finding about our writer.
3. File > Download > Microsoft Excel (.xlsx) → `fixtures/golden/gsheets/canonical.from-simple-excel.xlsx`.
4. Register the re-export and run the oracle over it:

```
node fixtures/register.mjs golden/gsheets/canonical.from-simple-excel.xlsx --id golden-canonical-gsheets-resave-simple-excel --generator "Google Sheets" --provenance "manual:golden/simple-excel/STEPS.md" --license "Google Sheets export" --tags kind:golden,generator:gsheets,policy:truncate-32767 --expected canonical/canonical.json --notes "<notices seen>"
npm run oracle -- --fixtures golden-canonical-gsheets-resave-simple-excel --readers simple-excel,sheetjs,office-kit --label gsheets-on-ours
```

5. Add the new fixture to `test/corpus-policies.json` with the categories that run reports and a reason for each.
   A category with no explanation is a bug to chase, not a policy to write.

### 2. Apple Numbers

1. Open `canonical.xlsx` in Numbers (File > Open). Write down every line of the import warning sheet.
2. Walk the checks above. Known Numbers behaviour from the ExcelJS golden: unsupported formulas are replaced by
   their last calculated value, and hidden sheets are made visible - expected, still worth recording.
3. File > Export To > Excel… > "Include a summary worksheet" OFF > Next > save as
   `fixtures/golden/numbers/canonical.from-simple-excel.xlsx`.
4. Register and run the oracle the same way, with `--id golden-canonical-numbers-simple-excel`,
   `--generator "Numbers 14.4"`, `--tags kind:golden,generator:numbers,policy:truncate-32767`.

### 3. Excel for Windows

The macOS oracle already opens all three files with no repair prompt; this checks that the Windows build agrees,
since it is stricter about some parts than the Mac one.

1. On a Windows machine with Excel (any recent 365 build), open `canonical.xlsx`, `canonical.inline.xlsx` and
   `canonical.zip64.xlsx`.
2. A **repair prompt** ("We found a problem with some content…") is a hard failure: keep the recovery log the
   dialog offers and file it with the file that produced it. So is a silent repair - after opening, check
   File > Info for a recovery notice.
3. Walk the checks above in each file, then Save As over a copy and confirm Excel saves without complaint.
4. Record the Excel build number and the verdict below. If a file needed repair, copy it and its recovery log
   into the repo so the failure is reproducible, and open an issue with the catalog id it breaks.
