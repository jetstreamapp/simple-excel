# 03 — XLSX library landscape (cross-language survey)

## Purpose

Jetstream is replacing SheetJS CE because it materializes the whole workbook — and the whole sheet XML string — in memory (`RangeError: Invalid string length` at ~958k rows, `Invalid array length` at ~18M cells). Before choosing between adopting `@office-kit/xlsx` and hand-rolling a zero-dependency streaming engine, this survey records how xlsx libraries across languages achieve bounded memory, handle strings, perform, and are licensed — and, most valuable, which bugs and edge cases their changelogs and issue trackers have already paid for.

_Accurate as of 2026-09-11._ Claims that could not be confirmed against a primary source are marked "(unverified)".

---

## 1. Three architectures that achieve bounded memory

Every library that handles "millions of rows" lands on one of three patterns. DOM libraries (SheetJS CE, openpyxl default mode, ClosedXML, PhpSpreadsheet, umya-spreadsheet, xlnt, caxlsx, rubyXL) are the unbounded fourth category, listed only for their lessons.

### 1a. Row-callback SAX readers

The reader locates `xl/worksheets/sheetN.xml` via `[Content_Types].xml` + `_rels` and pushes it through an event parser, emitting one row at a time. Only the shared string table (SST) must stay resident, because `<c t="s"><v>17</v></c>` indexes into it.

- **Java**: POI `XSSFReader` + `SheetContentsHandler`; `excel-streaming-reader` (SST optionally spilled to an H2 MVStore temp file); dhatim fastexcel-reader; EasyExcel/FastExcel.
- **.NET**: ExcelDataReader, Sylvan.Data.Excel, MiniExcel `Query`, Open XML SDK `OpenXmlReader`.
- **JS**: ExcelJS `WorkbookReader`, xlstream, xlsx-stream-reader, `@office-kit/xlsx` `loadWorkbookStream().iterRows()`; SheetJS only in Pro.
- **Python**: openpyxl `read_only=True`. **Ruby**: creek, roo `each_row_streaming`. **PHP**: OpenSpout, fast-excel-reader. **Elixir**: xlsxir, xlsx_reader. **Julia**: `XLSX.openxlsx(enable_cache=false)` + `eachtablerow`. **C**: xlsxio. **Rust**: calamine's streaming cell-record API (0.36.0).

### 1b. Row-flush streaming writers (inline strings or bounded SST)

The writer emits static parts first, then streams `<row>` elements into the sheet entry as rows are appended; each row goes to the zip deflater immediately. Two string strategies:

- **Inline strings** (`t="inlineStr"><is><t>…`): zero writer-side state, larger files. apify/xlsx-stream and xlsx-write-stream, LargeXlsx (default), dhatim fastexcel (unverified), ExcelJS `WorkbookWriter` unless `useSharedStrings`, rust_xlsxwriter/libxlsxwriter `constant_memory` (per rust_xlsxwriter #111; unverified against source).
- **Shared strings kept in RAM**: xlsxtream (optional), LargeXlsx (optional), excelize `StreamWriter` (optional), MiniExcel, `@office-kit/xlsx` write-only mode (unbounded SST serialized at `finalize()`; verified in 10 at 0.11.0). Bounded only by _unique_ strings — LargeXlsx's README warns that many distinct strings "may cause high memory consumption".

Shared constraint: rows must be written in ascending order, and row-spanning features (tables, merges, autofilter) are limited or declared up-front. XlsxWriter's docs, excelize's docs and pandas #11703 ("only the last row is written") document the failure mode.

### 1c. Temp-file spill writers

The writer keeps a sliding window of rows in memory, flushes older rows to a temporary file (optionally gzipped), and assembles the zip at `close()`. This decouples memory from row count without forcing strictly sequential writes inside the window.

- Apache POI `SXSSFWorkbook` (`rowAccessWindowSize`, default 100; `setCompressTempFiles`), and its NPOI port.
- libxlsxwriter / XlsxWriter / rust_xlsxwriter `constant_memory` (one-row window to a temp file; `tmpdir` configurable).
- excelize `StreamWriter` (temp file per sheet; `TmpDir` since 2.10.0) and excelize `Rows()` reader (spills large sheet XML).
- tealeg/xlsx v3 `UseDiskVCellStore` (disk-backed cell store; its `StreamFileBuilder` was dropped in v3 as "difficult to maintain").

Recurring lesson: `/tmp` is often tmpfs, so "constant process memory" silently becomes "plus a growing RAM disk" (libxlsxwriter docs), and cleanup on crash is the caller's problem. Browsers have no temp files; OPFS/IndexedDB is the only spill target.

Lessons from the JS ecosystem:

- **SheetJS**: a wrong self-reported `<dimension ref>` throws `RangeError` on read ([#3304](https://git.sheetjs.com/sheetjs/sheetjs/issues/3304)); `nodim: true` recomputes the range from actual cells. Its regex-based XML handling is what made CVE-2024-22363 possible.
- **ExcelJS**: streaming `_parseSharedStrings` pushed each rich-text `<r>` run as a separate SST entry, shifting every later index ([#1431](https://github.com/exceljs/exceljs/issues/1431)); stream reads OOM'd on a 6M-row file ([#355](https://github.com/exceljs/exceljs/issues/355)); "Invalid string length" on write even via the stream API ([#1868](https://github.com/exceljs/exceljs/issues/1868), [#709](https://github.com/exceljs/exceljs/issues/709)) — a streaming façade over DOM code is not enough; every intermediate string must be bounded.
- **@office-kit/xlsx**: open [#131](https://github.com/office-kit/xlsx/issues/131) — numeric character references (`&#xD;`) in inline strings are not decoded; inline and shared string paths must share one text decoder.
- **xlsx-stream-reader / xlstream**: a forward-only reader needs `xl/sharedStrings.xml` _before_ the sheets in the archive; writers do not guarantee that, which is why several readers extract to a temp dir or buffer the whole input (partially unverified).

Lessons from Rust:

- **calamine**: 0.36.0 broke Strict OOXML (`purl.oclc.org`) `_rels/.rels` links, fixed in 0.36.1; 0.35.0 had to ignore namespace _prefixes_ on relationship ids; 0.33.0 added protection against memory exhaustion from malicious ODS; 0.30.1 fixed xls SSTs with a wrong declared unique count. Each is a reader-robustness rule below.
- **calamine** perf work in 0.34–0.36 was pure allocation discipline: buffer reuse, `fast_float2` for `<v>`, zero-copy attribute extraction, `local_name` matching without allocating.
- **umya-spreadsheet**: a full `Style` struct per cell instead of an index into `cellXfs` is the single decision behind its 1 GB footprint — intern styles exactly as the file format does.

Lessons from Go:

- **excelize**: out-of-order `StreamWriter.SetRow` silently yields a file Excel reports as damaged (docs); the writer patches the `<dimension>` placeholder after streaming by seeking back into its temp file, which a pure forward stream cannot do; users still OOM by materializing all rows before `SetRow` ([#590](https://github.com/qax-os/excelize/issues/590)). 2.10.0 added `TmpDir` and `SetZipWriter` because deployers needed control over spill location and zip behaviour.
- **tealeg/xlsx**: dropping its streaming builder as "difficult to maintain" is the clearest evidence that a streamer bolted onto a DOM library carries its own maintenance cost.

Lessons from Python:

- **openpyxl** read-only mode "relies on … the dimensions" declared by the producer; with a wrong `<dimension>` (common) `ws.reset_dimensions()` must be called or rows are silently truncated — a second confirmation of the SheetJS `nodim` lesson. Read-only workbooks hold the zip open and must be closed explicitly.
- **openpyxl** ships `openpyxl.utils.escape` implementing `_xHHHH_` for control characters < 0x20 in both directions, because Excel writes `\r` as `_x000D_` inside `<t>`.
- **XlsxWriter**: `constant_memory` disables `add_table()` and limits `merge_range()`/`set_row()` to the current row — the feature cut a streaming writer must make explicit in its API. [#428](https://github.com/jmcnamara/XlsxWriter/issues/428) shows Excel rejecting Unicode noncharacters that are valid UTF-8.
- **pandas + constant_memory** ([#11703](https://github.com/pandas-dev/pandas/issues/11703)): a column-major caller produced a file containing only the last row — streaming writers must fail loudly, not drop silently, on non-monotonic row access.

Lessons from Java:

- **POI ZipSecureFile**: default `MIN_INFLATE_RATIO = 0.01` (fail if a part inflates > 100×) plus `MaxEntrySize` — and a steady stream of false positives on _legitimate_ repetitive sheets (Red Hat, IBM, B4X reports; SXSSF-generated templates trip POI's own reader). The guard is right; the threshold must be tunable and the error must name the part.
- **POI SXSSF**: rows outside the window "cannot be accessed anymore" and the API throws — the correct behaviour. Its `_xHHHH_` handling has had bugs of its own (NPOI 2.7.4 "wrong escape sequence for carriage returns").
- **excel-streaming-reader** ([PR #105](https://github.com/monitorjbl/excel-streaming-reader/pull/105)) fixed SST parsing with the cache enabled — SST parsing is the most bug-prone part of every streaming reader surveyed.

## 3. Cross-cutting lessons

Rules that are independent of engine choice; each cites the library that paid for it.

1. **Decide ZIP64 before writing the first byte, and treat the zip layer as part of the format contract.** When streaming, the local file header precedes the sizes; Excel opens 32-bit archives fine but rejects inconsistent headers, and "version needed" must be 4.5 in the local header if an entry might exceed 4 GiB ([rzymek](https://rzymek.github.io/post/excel-zip64/); [minizip-ng #894](https://github.com/zlib-ng/minizip-ng/issues/894), where auto-ZIP64 produced files Excel called invalid; [libxlsxwriter #228](https://github.com/jmcnamara/libxlsxwriter/issues/228); [LargeXlsx #3](https://github.com/salvois/LargeXlsx/issues/3); [fflate #81](https://github.com/101arrowz/fflate/issues/81)). Use data descriptors (bit 3) consistently for every entry, and test output in Excel, LibreOffice and Google Sheets — xlsxio's libzip builds produced files LibreOffice could not open.
2. **Escape control characters as `_xHHHH_`, unescape on read, and preserve whitespace.** ECMA-376 `ST_Xstring`: characters illegal in XML 1.0 are written as `_x000D_`-style escapes; a literal `_x` must itself become `_x005F_x` (openpyxl `utils.escape`; XlsxWriter; libxlsxwriter #189). Tab, LF and CR may instead be numeric character references, which readers must decode in inline strings too (office-kit #131). Any `<t>` with leading/trailing whitespace needs `xml:space="preserve"` or Excel trims it.
3. **Serial 60 is 1900-02-29.** Excel deliberately treats 1900 as a leap year for Lotus 1-2-3 compatibility ([Microsoft](https://learn.microsoft.com/en-us/troubleshoot/microsoft-365-apps/excel/wrongly-assumes-1900-is-leap-year)); serials < 61 are off by one relative to a correct calendar, and the `date1904` workbook property shifts the epoch entirely. Convert through an explicit epoch table, never through `Date` arithmetic alone.
4. **Dates are numbers plus a number format.** Detect by built-in `numFmtId` (14–22, 45–47) and by scanning custom format codes for date tokens outside quoted/bracketed sections (openpyxl `is_date_format`, calamine and readxl all use this heuristic; nobody has a better one).
5. **Never hard-code part paths.** Resolve `xl/workbook.xml` through `_rels/.rels` and sheets through `xl/_rels/workbook.xml.rels`; accept relationship ids with namespace prefixes (calamine 0.35.0) and Strict OOXML namespaces/relationship types under `purl.oclc.org/ooxml/` (calamine 0.36.1 regression, XLSX.jl #328, Open XML SDK #393).
6. **Tolerate missing or jumping `r` attributes** on `<row>` and `<c>` with running counters (box/spout #267; several readers still crash on this).
7. **Do not trust `<dimension>`** (SheetJS `nodim` + #3304; openpyxl `reset_dimensions`). Use it only as a progress hint; derive the true extent from the cells.
8. **Treat DOCTYPE as hostile.** Reject any DTD, external entity or entity expansion in every part (PhpSpreadsheet CVE-2018-19277 and CVE-2024-45293; fast-xml-parser CVE-2023-34104; "billion laughs"). A SpreadsheetML-subset parser that knows only the five predefined entities and numeric references (saxes' model) removes the attack surface by construction.
9. **Guard against zip bombs with configurable, part-named thresholds.** POI's `MIN_INFLATE_RATIO = 0.01` and `MaxEntrySize` catch bombs but also fire on legitimate repetitive sheets — report the ratio and the part, let callers raise the limit (POI ZipSecureFile; calamine 0.33.0), and also cap total inflated bytes and entry count.
10. **SST parsing is where streaming readers break.** Concatenate all `<r>` runs of an `<si>` into one entry, skip `<rPh>` phonetic runs, keep empty `<si/>` as empty strings, ignore the declared `count`/`uniqueCount` (ExcelJS #1431; Spreadsheet::XLSX CPAN #43247; ExcelDataReader #12; PhpSpreadsheet #1560; calamine 0.30.1; excel-streaming-reader PR #105).
11. **Inline and shared strings must be interchangeable.** Readers must handle `t="s"`, `t="inlineStr"` (with `<is><t>` _and_ `<is><r>`), `t="str"`, `t="b"`, `t="e"`, `t="d"` and untyped numbers; writers should default to inline for streaming and offer SST as an opt-in bounded by unique-string count (LargeXlsx README; ExcelJS `useSharedStrings`; excelize StreamWriter).
12. **Sequential rows only — and say so loudly.** Every row-flush writer forbids revisiting a flushed row; the good ones throw, the bad ones write a corrupt file or drop rows (excelize docs; pandas #11703).
13. **Archive entry order matters for forward-only readers.** `xl/sharedStrings.xml` and `xl/styles.xml` may follow the sheets; a reader over a non-seekable stream must buffer or read the central directory first (xlsx-stream-reader; ExcelDataReader copies non-seekable streams to memory — partially unverified). Writers should emit SST/styles _before_ sheets, which inline strings make trivial.
14. **Temp-file spill is not free.** tmpfs-backed `/tmp` turns disk spill into RAM (libxlsxwriter docs); temp dirs must be configurable (excelize `TmpDir`, POI, libxlsxwriter `tmpdir`) and cleaned on failure. Browsers have none — OPFS is the only spill target.
15. **Intern styles.** Per-cell style objects rather than `cellXfs` indexes took umya-spreadsheet from 1 MB on disk to > 1 GB in RAM (#165); ClosedXML's 0.103 string dedupe cut memory ~2.8×.
16. **Validate scalar inputs before serialization.** NaN/±Infinity, out-of-range dates, Unicode noncharacters and strings > 32,767 characters all yield files Excel refuses (libxlsxwriter 1.2.4; XlsxWriter #428; Microsoft [specifications and limits](https://support.microsoft.com/en-us/excel/excel-specifications-and-limits): 1,048,576 rows × 16,384 columns, 32,767 characters per cell).
17. **Every in-memory buffer is a ceiling.** V8 string length (SheetJS, ExcelJS #1868), V8 array length (SheetJS #2539), .NET `MemoryStream` 2 GB (ClosedXML #2734), 32-bit list indexes (pylightxl). Never concatenate a sheet, an SST or a zip entry into one string or array.
18. **Allocation discipline is the performance story.** calamine's 0.34–0.36 gains came from buffer reuse, zero-copy attribute reads and `fast_float`; Sylvan's .NET lead is "lowest allocating"; dhatim fastexcel's writer is one reusable 512 K-char buffer. Per-cell allocations, not parsing algorithms, dominate.

## 4. Implications for Jetstream

1. **Both options converge on the same architecture.** Every bounded-memory library surveyed is a row-callback SAX reader plus a row-flush inline-string writer (temp-file spill only where a filesystem exists). `@office-kit/xlsx` already implements exactly this (`loadWorkbookStream`, `createWriteOnlyWorkbook`); a hand-roll would rebuild it, not improve on it.
2. **The expensive part is the conformance corpus, not the streaming code.** office-kit's ~2100 tests, openpyxl fixture submodule and 3-tier validator are what a hand-roll cannot cheaply reproduce. If Jetstream hand-rolls, vendor those fixtures (MIT) as the acceptance suite; lessons 5–11 are the minimum edge-case matrix either way.
3. **Dependency risk is concentrated in fast-xml-parser.** Three CVEs (prototype pollution, DOCTYPE ReDoS, ReDoS) in an object-tree parser Jetstream would expose to untrusted uploads in the API, extension and desktop app. If adopting, confirm which parts office-kit routes through fast-xml-parser vs saxes and that DOCTYPE is rejected first; a hand-rolled SpreadsheetML-subset SAX parser removes the bug class. saxes is stable but unreleased for ~5 years; fflate for 19 months.
4. **fflate's 4 GiB per-entry cap bites at Excel's own limits.** A 1,048,576-row sheet with ~50 inline-string columns is roughly 2–4 GB of uncompressed XML, so "entries ≤ 4 GiB" is not academic. Either option needs a zip writer that declares ZIP64 in local headers up-front and streams through the deflater; a hand-roll can use native `CompressionStream('deflate-raw')` (Chrome 80+, Firefox 113+, Safari 16.4+, Node 21.2+ — all Jetstream targets) plus ~300 lines of zip container code; zip.js is the off-the-shelf alternative.
5. **In the browser the SST is the only unbounded structure on read**, and reading user workbooks (load records, bulk update from file) is a first-class path. Store the SST as a compact string array, optionally spill to OPFS for pathological files (Jetstream already has an OPFS store for data history), and offer a skip-SST/styles option like ExcelJS' `sharedStrings: 'ignore'` for column-sniffing passes.
6. **Inline strings are the right write default for Jetstream's exports.** Query and bulk-job results are mostly unique per cell (Ids, names, timestamps), so an SST would barely shrink the file while growing linearly in RAM; Excel re-shares strings on the user's first save anyway.
7. **The 32,767-character cap, NaN/Infinity and `_xHHHH_` escaping belong in the engine, not the callers.** Jetstream already hit the 32,767 cap in production; the engine should truncate-or-throw predictably and escape centrally (lessons 2 and 16).
8. **Zip-bomb and DOCTYPE guards are required for the API and extension regardless of engine.** Adopt POI-style inflate-ratio and max-entry-size checks with configurable thresholds and part-named errors (lesson 9); neither fflate nor zip.js enforces this for you (unverified for zip.js).
9. **Bus factor cuts both ways.** office-kit is one responsive maintainer and pre-1.0 (API may shift); a hand-rolled engine's maintainer is Jetstream, which has already killed one engine (excelize-wasm) at a performance gate. Either choice should sit behind the existing engine boundary and `npm run bench --` harness so switching stays cheap.
10. **Styles scope favours neither option.** Jetstream needs a handful of interned `cellXfs` (header bold, date/datetime formats, text-vs-number), which a hand-roll can emit as a static `styles.xml`; office-kit's full styling is a bonus.
11. **Multi-runtime is a verification task, not a design fork.** office-kit targets Node 22+ and modern browsers; Jetstream needs Node 24, Chromium (web, Electron renderer) and the MV3 service worker. `CompressionStream` and Web Streams exist in all of them; confirm office-kit has no Node-only imports on its browser path before adopting.
12. **Suggested ADR framing:** adopt `@office-kit/xlsx` behind the engine interface _if_ (a) its browser path is dependency-clean and DOCTYPE-safe and (b) the 4 GiB entry cap is accepted as a documented limit; otherwise hand-roll a ~2–3k-line streaming subset (zip container + SAX subset + row writer + interned styles) validated against the office-kit/openpyxl fixture corpus, using the cross-cutting rules as the test plan.
