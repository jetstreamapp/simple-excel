# 08 Migration plan

How Jetstream moves from SheetJS CE to `@jetstreamapp/simple-excel`, site by site: the exact call each place becomes, the behaviour differences the app has to absorb, how the work is delivered on each surface, the rollout order, and the hardening candidates that were deliberately left unimplemented.

_Accurate as of 2026-09-12 (branch chore/xlsx-hand-roll)._

The engine question is settled (ADR-008 addendum): this repository is the replacement, and every API named below is one that exists in `src/index.ts` today, not a proposal. Call-site line numbers come from `01-jetstream-usage-inventory.md` and will drift. The **parity test** column names the suite in this repository that proves the mapping; a Jetstream-side spec is named only where the repo suite cannot cover it.

## 1. The adapter

One module in `libs/shared/ui-utils` owns every call into the engine. Nothing else in the repo imports `@jetstreamapp/simple-excel`, for the same reason nothing imports `xlsx` today except the six sites in 01 B1: the value contract (dates, `defval`, header naming, truncation, error copy) is a single decision, and it belongs in one file with one spec.

The adapter owes the app four things the library deliberately does not do: converting a gapi binary string to bytes, computing column widths from content, spelling merge ranges in A1 notation, and deciding which of `sniff`'s verdicts routes to papaparse. Those are section 6.

Two read decisions stay explicit because they change data, not just types:

- `headers.filter(!startsWith('__empty'))` (`shared-ui-utils.ts:1333`) is replaced by `dropEmptyHeaders: true`. The columns were never mappable to anything useful, and the filter never matched, so this is a behaviour change being made deliberately.
- `dataHeaders.filter(Boolean)` (`load-records-multi-object-utils.ts:352`) removes a blank middle header and shifts every later column, misaligning the record. Replace it with an index-preserving map. That is a data-corruption bug, not a convention.

## 4. Delivery

ADR-004: the engine is thread-agnostic (no DOM globals beyond `TextEncoder`/`TextDecoder`, the compression streams and a duck-typed `Blob`), pure JS, no wasm. No CSP directive changes on any surface (01 C3, P1).

**Web.** Exports and large parses move into a real module worker, instantiated with the literal the bundler pattern-matches, exactly as `opfs-file-store.ts:134` does today:

```ts
new Worker(new URL('./spreadsheet.worker.ts', import.meta.url), { type: 'module', name: 'jetstream-spreadsheet' });
```

Inside it, `collectToBlob()` folds pending chunks into a sub-`Blob` every 32 MiB and drops the arrays, so the JS heap stays flat and Chromium pages the data out to disk; the finished `Blob` transfers back to the main thread by reference and goes straight to `saveFile`. `onProgress` (every 5,000 rows) and `sink.bytesWritten` drive the UI over the existing job message protocol, and `signal` makes cancel real. Small files stay on the main thread — the worker round trip is not free.

**Desktop.** Electron gets a streaming sink instead of a `Blob`: the renderer's sink forwards each chunk over IPC and the main process pipes it into `createWriteStream`, which `file-download.service.ts` already does for zips and Bulk API files. Either direction of the adapter pair works — `fromWritableStream(stream)` when the main process hands back a `WritableStream`, `toWritableStream(sink)` when the IPC bridge wants to `pipeTo` — so nothing accumulates in the renderer and the `will-download` / `downloadPreferences.downloadPath` detour is only needed for the small-file `Blob` path.

**Extension (MV3).** `script-src 'self'` and no `blob:` workers, so the worker must be a bundled same-origin file; the literal-URL pattern produces exactly that. If the extension build cannot emit the extra chunk, the extension keeps the main-thread path with `collectToBytes({ maxBytes })` and the size gate below — the library itself needs no change either way, and there is no eval and no wasm to grant.

**Canvas.** Main thread with yielding, and the tightest `maxBytes`: it is an iframe inside Salesforce and the memory is not ours.

**The `estimatedBytes` gate.** Before starting an export, estimate the output from `recordCount × fieldCount` (plus subquery sheets) and warn rather than disable; while it runs, `onProgress({ bytesOut })` and `sink.bytesWritten` give a live number. Two places need it: Firefox and Safari keep `Blob` data in memory (Chromium does not), and `collectToBytes` has a hard `maxBytes` that raises `LIMIT_EXCEEDED`. A warning at a few hundred megabytes on those browsers is honest; a hard block is not needed on Chromium or on desktop, where the bytes go to disk.

**Lifting the 500,000-row CSV-only rule.** `REQUIRE_BULK_API_COUNT` (`RecordDownloadModal.tsx:132`) exists because the SheetJS build crossed V8's ~512 MB string cap; the comment says so. The streaming writer never builds a string past 64 KiB and never holds a worksheet, so an xlsx export is bounded by the sink, not by the row count. Feed `writeRows` from an async iterable over the paged query or Bulk API results:

```ts
const sheet = workbook.addSheet('records', { header: fields, rowCount: recordCount });
await sheet.writeRows(recordPages()); // AsyncIterable<CellInput[]>
await sheet.close();
```

`rowCount` is worth passing: it enables `<dimension>` and lets the zip64 decision be made up front (ADR-002). What stays is Excel's own limit — 1,048,576 rows per sheet — which the UI should state instead of the current 500,000-row CSV downgrade.

**Feature flag.** One flag, `xlsxEngine: 'sheetjs' | 'simple-excel'`, read in exactly two places — `parseFile` and `prepareExcelFile` — plus the worker entry, so one switch rolls the whole surface. It rides the existing feature-flag heartbeat, so desktop, extension and canvas honour it without a new binary.

**Rollback.** While both engines are in the bundle (steps 1–4), rollback is flipping the flag: no rebuild, no release, and desktop and extension pick it up on their next heartbeat. The cost of that window is the `xlsx` tarball staying in the bundle. After step 5 rollback is a revert and a release, which is why step 5 waits a full release after the flags default on. The read path is the risky half (section 3, differences A–M are all reads); the write path either produces a file that opens or does not, and the oracle in this repository already answers that question.

**Manual checks that no suite covers:** a Google Drive upload of a workbook we wrote (Drive converts it to a native Google Sheet, so the file has to survive Google's importer), the Electron open-with path for both `.csv` and `.xlsx`, and a Drive pick on each of the four surfaces.

**jsdom caveat.** jsdom's `Blob` does not interoperate with Node's `CompressionStream` (cross-realm web streams). This repository's tests run under vitest `environment: 'node'`. Jetstream specs that exercise the writer keep the `globalThis.Blob = NodeBlob` setup from `libs/shared/ui-data-history/src/test-setup.ts`; the library never passes a `Blob` into a stream itself (it reads Blobs with `slice().arrayBuffer()`).

## 6. API gaps found while mapping

Nothing here blocks the migration; each is either a caller-side computation by design or an export that has since been added.

1. **Column auto-width from content is caller-side.** `getMaxWidthFromColumnContent` stays in Jetstream: the library takes `ColumnOptions.width` as a number in Excel character units and has no auto-fit, which is right for a streaming writer that never sees two rows at once. The helper's return type changes from `XLSX.ColInfo[]` to `ColumnOptions[]` — structurally identical — and must clamp at 255.
2. **Resolved: sheet-name sanitizer exported.** `sanitizeSheetName(name, taken)`, `isValidSheetName(name)` and `MAX_SHEET_NAME_LENGTH` are in `src/index.ts` (commit 1e95115). Callers that key data by sheet name _before_ writing — `sobject-export-utils.ts:204`, `getSubquerySheetName`, the `_ParentId` cross-references in `getMapOfBaseAndSubqueryRecords` — call `sanitizeSheetName` with the same `taken` set to get the name the writer will pick.
3. **Resolved: cell-reference helpers exported.** `formatRef`, `formatRange`, `parseRef`, `parseRange`, `columnLetters`, `columnIndexOf`, `MAX_ROWS` and `MAX_COLUMNS` are in `src/index.ts`. The Permission Manager's 0-based `{ s: { r, c }, e: { r, c } }` pairs become `sheet.merge(formatRange(s.r, s.c, e.r, e.c))`.
4. **Resolved: `SNIFF_BYTES` exported.** Callers pass `bytes.subarray(0, SNIFF_BYTES)` instead of hard-coding `65_536`.
5. **Array mode has no `defval` and no width.** `RowsOptions` carries neither, so a caller reproducing `sheet_to_json({ header: 1, defval: '' })` pads rows itself (difference G). **Proposal (optional):** accept `defval` in array mode, or expose the sheet's declared column count so the caller can pad without guessing.
6. **No binary-string input.** `SourceInput` is `ArrayBuffer | SharedArrayBuffer | ArrayBufferView | Blob | RandomAccessSource` (any typed array, checked cross-realm); a string is refused with `NOT_XLSX` and a hint to convert it. The gapi Drive picker produces a binary string. This is deliberate — the core entry stays browser-safe and type-clean — and the adapter converts once, or the picker is changed to fetch bytes. No change proposed.
7. **No one-shot multi-sheet helper.** Every caller writes the same open/addSheet/writeRows/close loop. That belongs in Jetstream's adapter (`prepareExcelFile` _is_ that helper), not in a library whose whole point is that nothing is materialized. No change proposed.

## 7. Immediate hardening candidates (documented only; the user chose not to implement these yet)

These are independent of the engine choice and could ship as one small PR with parity tests. Recorded here so the reasoning is not lost. Items 1 to 3 apply while SheetJS is still in place — the migration removes the underlying causes.

1. **`dense: true`** on the four Permission Manager sheets (`permission-manager-export-utils.ts:188, 234, 282, 419`). `prepareExcelFile` already uses dense sheets, which is why query exports survive far larger sheets; the sparse sheets hit V8's own-property cap near 8.4 million cells and throw `RangeError: Too many properties to enumerate`.
2. **Cell-count guard** in `RecordDownloadModal.tsx` and mirrored in `JobWorker.ts` for the `xlsx` cases. Derivation: V8's maximum string length is 2^29 - 24 (about 537M UTF-16 units); SheetJS builds each sheet's XML as one string at roughly 30 to 55 characters per cell, so the string cap alone falls between 10M and 18M cells, consistent with the 958k x 10 `Invalid string length` failure and the 172k x 107 (18M-cell) `Invalid array length` failure. Memory fails earlier: 3.2 GB peak measured at 2M cells (about 1.6 KB per cell) against a renderer heap that is often 2 to 4 GB. Proposed constants in `libs/shared/constants`: `XLSX_MAX_CELLS = 1_000_000` (hard: the xlsx radio is disabled with "Exports over 1,000,000 cells must use CSV") and `XLSX_WARN_CELLS = 250_000` (banner: large xlsx exports may take a while), where cells = `recordCount x fieldsToUse.length` plus an estimate for subquery sheets. Re-tune from `06-performance-baseline.md` once the new engine lands.
3. **Truncation on the Permission Manager path:** export `truncateCellsForExcel` from `shared-ui-utils.ts` and apply it in each `generate*Worksheet` before `aoa_to_sheet` (the sheet-map form of `prepareExcelFile` cannot be used because it drops `!cols` and `!merges`); thread `onCellsTruncated` to the existing toast.
4. **Input size and magic-byte guard:** no limit exists on local, Drive or Electron open-with spreadsheet bytes. Add a byte-size check before parsing (for example 100 MB on web, extension and canvas, 500 MB on desktop) and a magic-byte sniff so CFB files surface the `password-protected` or legacy-format message and CSV bytes stop entering the xlsx branch. The migration supplies the sniff (`sniff`, section 2.2) but not the size cap.
5. **`MIME_TYPES.XLSX`:** `application/octet-stream;charset=utf-8` at `shared-constants.ts:138` while `XLSX_OPEN_OFFICE` holds the real type and `Jobs.tsx:195` already special-cases xlsx for Drive. At minimum drop the meaningless `charset`.
6. **The two latent read bugs** (section 3): the lowercase `__empty` filter and the `filter(Boolean)` index shift. Fix deliberately or pin as intentional.
