# 08 Migration plan

How Jetstream moves from SheetJS to the selected engine, site by site, and the hardening candidates that were deliberately left unimplemented.

_Accurate as of 2026-09-11 (branch chore/xlsx-hand-roll)._

The engine is undecided until `10-office-kit-evaluation.md` records ADR-008; the API names below use the facade vocabulary of `07-reference-architecture.md` (`createWorkbookWriter`, `openSpreadsheet`, `SheetHandle.rows`, `head`) and map onto `@office-kit/xlsx` (`createWriteOnlyWorkbook`, `loadWorkbookStream`, `iterRows`) if that engine is adopted. Call-site details come from `01-jetstream-usage-inventory.md`.

## 2. Migration order

1. **Read path first, behind a snapshot and parity suite.** Follow `libs/salesforce-api/src/lib/__tests__/xml-parsing-snapshot.spec.ts` (the fast-xml-parser to `@jetstreamapp/simple-xml` swap): a spec that builds every existing test workbook (today built with `XLSX.utils.aoa_to_sheet`) plus every fixture in `fixtures/`, reads each with SheetJS using the exact Jetstream options and with the new engine, and asserts `toEqual` on `{ data, headers }`. Differences are classified as engine bug, SheetJS bug, or an intentional fix (`__EMPTY` filtering, index shift) and pinned either way. Ship `parseFile` on the new engine behind a feature flag (`libs/shared/ui-utils`), default off.
2. **`prepareExcelFile` in a real module worker.** Keep the sync shim for callers that need an `ArrayBuffer` (extension and canvas builds, the Google Drive upload job, tests). Add the streaming path for `RecordDownloadModal` and `JobWorker`, flag-gated, with progress and cancellation; web uses a `BlobCollector`, desktop streams over IPC to disk.
3. **Permission Manager** on the writer's widths, merges and date format; delete `excelWorkbookToArrayBuffer`.
4. **Remove the leaks:** `ensureXlsxCodepageTable` and the `cpexcel` import (legacy formats are rejected with a message instead), `XLSX.WorkBook` in `libs/types` (pickers return `SpreadsheetSource`), the `replace-package-deps.mjs` special case, the `build-electron.mjs` exclusion.
5. **Remove `xlsx`** from `package.json` when the flags are default-on for one release, then delete the flags.

Each step lands as its own PR with the parity suite green on both engines.

## 3. Feature flag and compatibility shim

- One flag, `xlsxEngine: 'sheetjs' | 'next'`, read by `parseFile` and `prepareExcelFile` (and the worker) so a single switch rolls the whole surface. Desktop, extension and canvas honor the same flag through the existing feature-flag heartbeat.
- The shim keeps `prepareExcelFile(...): ArrayBuffer` synchronous in name only where a caller needs bytes now; internally it runs the writer to a `Uint8ArrayCollector`. Because the new writer is async, the shim becomes `Promise<ArrayBuffer>` and the 30-odd callers that `await` inside handlers already tolerate that; the three that do not are updated in the same PR.
- The Google Drive upload job keeps receiving bytes (Drive converts to a Google Sheet); above the Sheets conversion cap the job uploads the raw `.xlsx` without conversion and says so.

## 4. Decisions to make explicit during migration

| Behavior                                                                 | Today                                          | Choice                                                                                                |
| ------------------------------------------------------------------------ | ---------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| `headers.filter(!startsWith('__empty'))` (`shared-ui-utils.ts:1333`)     | no-op; `__EMPTY` columns reach field mapping   | turn `skipEmptyHeaders` on and pin it; the columns were never mappable to anything useful             |

| CSV bytes reaching the xlsx branch                                       | SheetJS parses them                            | `openSpreadsheet` returns `kind: 'text'` and the papaparse branch handles it                          |
| `.xls`, `.xlsb`, `.ods` renamed to `.xlsx`                               | SheetJS parses them                            | clear error with a save-as instruction (user decision: legacy formats are out of scope)               |
| `MIME_TYPES.XLSX = 'application/octet-stream;charset=utf-8'`             | wrong type on the local Blob                   | switch to `XLSX_OPEN_OFFICE` after checking file-saver behavior in the Firefox extension and Electron |

## 5. jsdom caveat

jsdom's `Blob` does not interoperate with Node's `CompressionStream` (cross-realm web streams). The engine's own tests run under vitest `environment: 'node'`. Jetstream specs that exercise the writer through the shim keep the `globalThis.Blob = NodeBlob` setup used in `libs/shared/ui-data-history/src/test-setup.ts`, and the engine must never pass a `Blob` into a stream on its own (it reads Blobs with `slice().arrayBuffer()`).

## 6. Immediate hardening candidates (documented only; the user chose not to implement these yet)

These are independent of the engine choice and could ship as one small PR with parity tests. Recorded here so the reasoning is not lost.

1. **`dense: true`** on the four Permission Manager sheets (`permission-manager-export-utils.ts:188, 234, 282, 419`). `prepareExcelFile` already uses dense sheets, which is why query exports survive far larger sheets; the sparse sheets hit V8's own-property cap near 8.4 million cells and throw `RangeError: Too many properties to enumerate`.
2. **Cell-count guard** in `RecordDownloadModal.tsx` and mirrored in `JobWorker.ts` for the `xlsx` cases. Derivation: V8's maximum string length is 2^29 - 24 (about 537M UTF-16 units); SheetJS builds each sheet's XML as one string at roughly 30 to 55 characters per cell, so the string cap alone falls between 10M and 18M cells, consistent with the 958k x 10 `Invalid string length` failure and the 172k x 107 (18M-cell) `Invalid array length` failure. Memory fails earlier: 3.2 GB peak measured at 2M cells (about 1.6 KB per cell) against a renderer heap that is often 2 to 4 GB. Proposed constants in `libs/shared/constants`: `XLSX_MAX_CELLS = 1_000_000` (hard: the xlsx radio is disabled with "Exports over 1,000,000 cells must use CSV") and `XLSX_WARN_CELLS = 250_000` (banner: large xlsx exports may take a while), where cells = `recordCount x fieldsToUse.length` plus an estimate for subquery sheets. Re-tune from `06-performance-baseline.md` once the new engine lands.
3. **Truncation on the Permission Manager path:** export `truncateCellsForExcel` from `shared-ui-utils.ts` and apply it in each `generate*Worksheet` before `aoa_to_sheet` (the sheet-map form of `prepareExcelFile` cannot be used because it drops `!cols` and `!merges`); thread `onCellsTruncated` to the existing toast.
4. **Input size and magic-byte guard:** no limit exists on local, Drive or Electron open-with spreadsheet bytes. Add a byte-size check before parsing (for example 100 MB on web, extension and canvas, 500 MB on desktop) and a magic-byte sniff so CFB files surface the `password-protected` or legacy-format message and CSV bytes stop entering the xlsx branch.
5. **`MIME_TYPES.XLSX`:** `application/octet-stream;charset=utf-8` at `shared-constants.ts:138` while `XLSX_OPEN_OFFICE` holds the real type and `Jobs.tsx:195` already special-cases xlsx for Drive. At minimum drop the meaningless `charset`.
6. **The two latent read bugs** (section 4): the lowercase `__empty` filter and the `filter(Boolean)` index shift. Fix deliberately or pin as intentional.
